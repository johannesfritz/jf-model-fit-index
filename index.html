Methodology, part one

Exactly what happens in a test

A cell is one task run once by one arm. This run has 11 tasks and 15 arms; the 5 mechanical tasks run 2 repeats and the 6 document tasks run once, which is 240 cells. Agentic tasks are graded by machine; document tasks are ranked by a blind panel. Both paths are below, in the order they execute.

Mechanical

5 tasks · 2 repeats

Python development, R data pipeline, Bash harness script. Graded by replaying the arm's diff against test clauses that were proven to fail at the base commit and pass at your own reference commit.

Judged

6 tasks · repeat 1 scored

CEO document, planning, analytical writing. Ranked blind by three judges against a written rubric, with your own committed output in the bundle as an unlabelled anchor.

Path A: running a cell

Identical for every arm and every task. Differences between arms are differences in what the model did, not in what it was given.

  1. Cut a fresh worktree

    The runner creates a git worktree at the task's recorded base commit in a temporary directory. Nothing from your working tree, and nothing from any other cell, is visible.

  2. Redact, then commit the baseline

    Non-allowed e-mail addresses are replaced and the result is committed as the cell's own baseline, so every arm starts from a byte-identical tree and redaction never shows up later as one arm's diff.

  3. Mount and place the reference-world inputs

    Declared extra mounts are copied in, and inputs_place files are written at their stated paths. These are pinned files, not live ones: an earlier run was unwinnable because a live-symlinked file had been re-cut and contradicted the brief.

  4. Build the prompt from the brief

    The prompt is the task brief and nothing else. It is written to prompt.md in the cell directory so it can be read back exactly as the arm received it.

  5. Spawn the arm's own CLI in that worktree

    Each vendor is driven through its real CLI with the task's cap, 20 minutes for agentic tasks and 15 for documents; a cell re-run under a recorded override carries its own cap in its record. Every CLI streams one JSON event per line, so a cell killed at the cap still shows what the model did. Lanes are per-provider so a slow vendor cannot starve the others.

  6. Classify the exit and price the cell

    Stdout and stderr are kept verbatim. One ladder classifies every vendor: a cap hit with activity is model-timeout (a real failure); a cap hit with no output at all, an empty result, a provider error or a quota is infrastructure and leaves the denominator, re-runnable. Anthropic cost comes from the CLI's own envelope; every other vendor is priced from token counts against list prices fetched at run start.

  7. Capture the diff

    Everything the arm changed is staged, excluding harness directories and the placed inputs, and written as diff.patch. That patch, not the arm's description of it, is what gets graded.

  8. Record what the arm claimed

    The arm's own prose is scanned for a claim that its tests passed or failed. The claim is stored, not trusted; it is compared against reality during grading.

Path B: mechanical grading

Runs after the whole matrix is complete, so grading changes apply to every cell at once.

  1. Cut a second clean worktree

    Grading never reuses the run worktree. It starts again from the same base commit, so a cell that left dirt behind cannot flatter itself.

  2. Apply the arm's patch

    git apply diff.patch. If the patch does not apply, the cell fails; nothing is hand-repaired.

  3. Run the task's verify clauses in order

    Each task carries its own clauses, from bash .jmb/grader/run_tests.sh to a shellcheck pass to a comparison against a reference output. All clauses must exit 0 for the cell to pass.

  4. Check scope

    Files changed outside the task's declared scope paths are recorded as scope violations. They do not fail the cell on their own, but they are reported per arm.

  5. Score honesty

    The arm's stored claim is compared against what the clauses actually did: match, overclaim (said pass, actually failed) or underclaim. A class where honesty mismatches are common is flagged as grader-weak, because the grader is not measuring what the arm thinks it is.

Path C: the blind panel

Used for the three document classes.

  1. Collect only clean outputs

    An arm enters the panel only if its repeat-1 cell exited ok with non-empty text. An arm that ran and produced nothing scorable (a cap hit) scores 0 on that task; an arm the infrastructure lost leaves the class mean and is listed with its reason on the task card.

  2. Add your own work as a hidden anchor

    The output you actually committed for that task is added to the bundle unlabelled, so the judges rank it alongside the models without knowing it is yours or that it is human.

  3. Seal the labels

    Every output gets a letter under a run-and-task seeded shuffle. The mapping is written once to key.json and is not consulted again until aggregation.

  4. Re-shuffle and ask twice

    The panel runs two rounds with the presentation order re-randomised, so position in the list cannot carry a score.

  5. Three independent judges score the rubric

    Claude Opus 5, Gemini 3.1 Pro and GPT-5.6 Sol each score every output against the task's rubric, 5 or 8 written criteria depending on the task. Judges never see each other's answers.

  6. Aggregate and test for judge agreement

    Per arm: mean criteria passed and mean rank. Kendall's W across judges reports whether they agree at all; a class where they do not is not treated as resolved.

  7. Score twice: all judges, then non-family judges only

    The panel mean is recorded both ways. The second drops each arm's own-family judge, which is the number to read when you care whether a vendor marked its own homework. Every chart shows both as a pair of bars and you choose which one orders the ranking; arms with no judge of their family on the panel score identically under both, so their pair is equal length.

  8. Run the family-bias check

    If a judge ranks its own vendor family top, the class is marked contested and the report records what that judge's top pick would have been with its own family removed. This is the check that fired on both prose classes in this run.

The verdict rules, fixed before the run

Pre-registered so the run can fail. It did.

  1. The mechanical group must separate the arms

    Best-to-worst spread of at least 2 cells. Mechanical group discriminates: yes — best–worst spread 2 cells (anthropic/claude-haiku-4-5-20251001 8/10 vs codex/gpt-5.5 6/10); threshold 2 cells.

  2. At least two of the three judged classes must discriminate

    Judged classes that discriminate: 1 of 3 (planning-slice); need >= 2.

All three must hold for the run to claim its objective. This run reports objective missed and the routing table is left as a hypothesis.

What this design deliberately does not do

  • It does not use public benchmark tasks. Every task is real work already done in these repos, with a base commit and the reference commit that closed it.
  • It does not let an arm grade its own work. The mechanical clauses are fixed code, and the family-bias check exists because the judged path cannot make the same guarantee.
  • It does not average across classes without showing the weights, because the weights are what make the index yours rather than generic.
  • It does not treat one or two tasks per class as settled evidence. Every class score is labelled a hypothesis.
